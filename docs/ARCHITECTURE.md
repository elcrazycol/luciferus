# Как всё устроено

Документ для того, кто собирается читать или менять код. Здесь — устройство проекта
сегодня. Планы и история решений — в [`../PLAN.md`](../PLAN.md), гайд для авторов игр —
в [`SDK.md`](./SDK.md).

---

## Главный принцип

**Портал — это хост и кошелёк, а не игровой движок.**

Игры живут на своём хостинге, на любом движке и языке. Портал загружает их в iframe и
разговаривает через `postMessage`. Он не собирает игры, не билдит их и не хранит их код.

Отсюда следует почти всё остальное: тонкий SDK, скоуп-токены вместо доверия, проверка
origin в хендшейке и то, что единственное, чем игра распоряжается, — деньги одного
игрока в одной игре.

## Карта репозитория

```
apps/
  api/            Hono: REST + SSE, вся бизнес-логика
  portal/         Next.js: интерфейс, серверные действия, прокси потоков
  example-game/   эталонный слот: живая документация и фикстура тестов
packages/
  protocol/       типы и валидаторы, общие для API, портала и SDK
  fairness/       SHA-256, HMAC, вывод случайности, проверка раунда
  sdk/            то, что подключает игра (19 КБ, без зависимостей)
  db/             схема Drizzle, миграции, сиды
  config/         валюта и экономика в одном месте
infra/            docker compose: Postgres + Redis
docs/             этот файл, SDK.md
```

**`packages/protocol` — сердце связности.** Типы и схемы валидации описаны один раз и
используются всеми сторонами: форма заявки проверяется той же схемой, что и API; типы
карточки игры не дублируются в портале; константы протокола встраивания общие для SDK и
портала. Расхождение контракта становится ошибкой сборки, а не багом в рантайме.

**`packages/config` держит валюту в одном месте.** CrazyBucks (C$) описаны в
`packages/config/src/currency.ts`. Форк, который захочет переименовать монету, меняет один
файл — не ищет `C$` по всему коду.

## Деньги

### Леджер — источник правды

`ledger` — append-only журнал всех движений баланса. `wallets.balance` — материализованный
кэш, который обновляется **в той же транзакции**, что и запись в журнал.

```
любая операция
      │
      ▼
 BEGIN
   SELECT ... FROM wallets WHERE user_id = ? FOR UPDATE   ← блокировка строки
   SELECT ... FROM ledger WHERE idempotency_key = ?        ← идемпотентность
   UPDATE wallets SET balance = balance ± ?  RETURNING balance
   INSERT INTO ledger (...)
 COMMIT
```

Три детали, которые здесь принципиальны:

1. **Блокировка строки кошелька.** Все операции одного игрока выстраиваются в очередь.
   Без неё две одновременные ставки обе увидели бы достаточный баланс и увели его в минус.
   Есть тест: десять параллельных ставок по 100 при балансе 250 — проходят ровно две.
2. **Проверка идемпотентности — под блокировкой.** Если проверять ключ до неё, параллельный
   ретрай проскочит мимо ещё не закоммиченной записи и спишет деньги дважды.
3. **Арифметику делает Postgres.** Суммы ходят строками, `numeric(18,2)`, сравнение
   «хватает ли денег» считает база. Прогонять баланс через JS-числа нельзя.

Единственный путь изменения баланса — `applyEntry` в `apps/api/src/services/wallet.ts`.
Прямых `UPDATE wallets` в обход журнала в коде нет и не должно появиться.

### Почему не денормализовано

Статистика игр (число ставок, крупнейший выигрыш, последняя игра) считается агрегатом по
леджеру, а не хранится счётчиком в строке игры. Счётчик расходится с журналом при первом же
сбое, и потом никто не знает, какому числу верить. Агрегат всегда честный, а индекс
`ledger_game_idx` делает его дешёвым.

## Границы доверия

Игра — **недоверенный код на чужом домене**. Она не видит куки портала и не может ничего,
кроме того, что разрешает её скоуп-токен.

### Хендшейк

Инициатор — **портал**, а не игра. Это не симметрично, но так у игры нет причин постить в
`*`: она вообще не знает, кто её открыл, пока портал сам не представится.

```
Портал                                          Игра (iframe)
  │  casino:init { nonce, gameSlug, portalOrigin } │
  ├────────────────────────────────────────────────►│  адресат — объявленный origin
  │  casino:hello { nonce, sdkVersion }             │
  │◄────────────────────────────────────────────────┤  игра не постит в *
  │  casino:session { token, apiUrl, wallet, ... }  │
  ├────────────────────────────────────────────────►│  адресат — origin портала
```

Четыре проверки до выдачи сессии, все обязательны:

1. сообщение пришло из нашего iframe (`event.source`);
2. `event.origin` объявлен в манифесте игры;
3. `nonce` совпадает с выданным;
4. слаг игры совпадает с запущенной.

Не прошла любая — игра остаётся без сессии, а портал показывает причину.

### Игровой токен

Не JWT. У JWT есть заголовок с полем `alg`, которое атакующий может подменить; здесь
заголовка нет вовсе — алгоритм зашит в код, подписывается ровно одна строка. Формат:
`base64url(payload) + '.' + base64url(HMAC-SHA256(secret, payload))`.

Токен живёт два часа, привязан к одной игре и одному игроку и содержит `sid` — сессию
портала. Поэтому выход из аккаунта отзывает и игровой токен: проверка `sid` идёт на каждом
запросе.

### Куки и CORS

API не знает про куки. Сессионную куку держит портал на своём домене, а с API общается
Bearer-токеном. Поэтому прод не зависит от того, на одном домене портал и API или на разных.

CORS смонтирован на конкретные префиксы, а не на весь `/v1/*`. Это не косметика: Hono на
`OPTIONS` отдаёт preflight сразу и не передаёт управление дальше, поэтому общий CORS
перехватывал бы preflight игровых маршрутов и отвечал за них своей политикой. В браузере это
выглядело бы как «игра не может достучаться до API» без причины в консоли.

## Проверяемая честность

Commit-reveal на HMAC-SHA256, в обе стороны.

1. Портал заводит пару сидов и **сразу публикует** `sha256(серверный сид)`. Сам сид скрыт.
2. Клиентский сид виден игроку и может быть сменён.
3. Случайность раунда: `HMAC-SHA256(серверный сид, клиентский сид : номер)`.
4. Игра превращает число в исход по своей таблице весов.
5. Игрок раскрывает сид и пересчитывает любой раунд — в браузере.

Распределение ролей: случайность считает **сервер** (у игры нет серверного сида и быть не
должно — иначе она предсказывала бы раунды), а проверить её может **любой** после раскрытия.

Ключевая защита: сервер знает свой сид, поэтому пересчитывает случайность и сверяет с той,
что приложила игра, — **до списания ставки**. Подсунуть своё число игра не может.

Уникальный индекс `(user_id, game_id, pairId, nonce)` в журнале запрещает сыграть одним
номером дважды. Пара входит в индекс потому, что номер раунда имеет смысл только внутри
своей пары: после раскрытия новая пара начинает нумерацию с единицы.

Чего схема не доказывает — что игра **отобразила** исход честно. За это отвечает автор игры,
поэтому случайность раунда сохраняется в журнале и видна рядом с исходом.

## Realtime

Кошелёк публикует изменение баланса в Redis, подписчики получают его через SSE.

```
wallet.applyEntry ──► Redis pub/sub ──► SSE /v1/wallet/stream ──► прокси портала ──► EventSource
```

Три решения, которые стоит знать:

- **SSE, а не WebSocket.** Данные идут в одну сторону, `EventSource` сам переподключается
  после обрыва. Для «обнови цифру» этого достаточно и заметно проще. WebSocket понадобится
  для чата и presence — там двусторонний обмен.
- **Подписка на отдельном соединении.** Redis запрещает обычные команды на соединении в
  режиме подписки, поэтому переиспользовать основной клиент нельзя: rate limit сломался бы,
  как только первый игрок откроет поток.
- **Поток идёт через портал.** Токен сессии остаётся на сервере, `EventSource` не умеет
  отправлять заголовки, и CORS для потока не нужен.

Публикация — удобство, а не источник правды: недоступный Redis не роняет операцию, просто
интерфейс обновится позже.

## С чего начать чтение

1. `packages/config/src/currency.ts` — пять строк, но задают язык всего проекта.
2. `apps/api/src/services/wallet.ts` — ядро денег, комментарии объясняют каждое решение.
3. `packages/sdk/src/core.ts` — что видит автор игры.
4. `apps/portal/src/lib/embed-bridge.ts` — вся защита хендшейка в одном файле.
5. `apps/example-game/src/game.ts` — как это выглядит со стороны игры.

Тесты рядом с кодом и часто объясняют больше комментариев: `apps/api/tests/wallet.test.ts`
начинается с гонки параллельных ставок.
