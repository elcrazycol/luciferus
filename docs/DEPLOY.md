# Развёртывание

Проект рассчитан на `docker compose up` в чистом окружении, но на сервере, где уже
живут другие сервисы, есть свои ограничения. Здесь — оба случая.

---

## Обычный случай: своя машина

```bash
git clone https://github.com/elcrazycol/luciferus.git
cd luciferus/infra

cp ../.env.example .env      # заполнить POSTGRES_PASSWORD, GAME_SESSION_SECRET,
                             # PUBLIC_API_URL, PORTAL_URL

docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml run --rm migrate
docker compose -f docker-compose.prod.yml run --rm seed
```

Портал окажется на `127.0.0.1:8080`, API — на `127.0.0.1:3001`. Наружу их отдаёт
обратный прокси: так TLS и домены живут в одном месте, а не внутри приложения.

### Что обязательно задать

| Переменная | Зачем |
|---|---|
| `POSTGRES_PASSWORD` | пароль базы; без него compose откажется стартовать |
| `GAME_SESSION_SECRET` | подпись игровых токенов. Сгенерировать: `openssl rand -hex 32` |
| `PUBLIC_API_URL` | адрес API, который получают игры в хендшейке. Он обязан совпадать с тем, что разрешено в CORS |
| `PORTAL_URL` | адрес портала; от него зависит CORS портальных маршрутов |

`API_URL` внутри стека — это **внутренний** адрес (`http://api:3001`): портал ходит в API
по сети compose. `PUBLIC_API_URL` — то, что видят игры. Это разные значения, и путать их
нельзя: игра обращается к API напрямую из браузера.

### Почему в compose есть лимиты памяти

У каждого сервиса стоит `mem_limit`. Это не перестраховка: при перерасходе Docker убьёт
именно этот контейнер, а не соседей на хосте. У портала дополнительно ограничена куча
Node (`--max-old-space-size`) — так он успевает собрать мусор вместо того, чтобы быть
убитым.

Фактическое потребление всего стека — около 130 МБ:

| Сервис | Лимит | Фактически |
|---|---|---|
| portal | 224 МБ | ~63 МБ |
| api | 128 МБ | ~34 МБ |
| postgres | 128 МБ | ~26 МБ |
| redis | 32 МБ | ~4 МБ |

## Случай сервера с другими сервисами

Если на машине уже что-то работает, сначала выясните, какие порты заняты:

```bash
ss -tlnp
```

**Ничего не публикуйте на 80 и 443, не проверив, кто их держит.** В нашем случае
на боевом сервере сложилась такая картина:

| Порт | Кто занял | Почему не трогать |
|---|---|---|
| 443 | VPN-ядро (Xray), конфиг приходит из панели | сломается VPN |
| 80 | свободен, но `certbot` в режиме `standalone` | продление сертификатов соседних доменов перестанет работать |
| 8443 | сервис с собственным TLS | сломается он |
| 2222 | VPN-нода | сломается VPN |

Отсюда правило: **порт 80 может быть занят certbot'ом, даже если сейчас никто не
слушает**. Проверьте `/etc/letsencrypt/renewal/*.conf` на `authenticator = standalone` —
если он там есть, порт 80 обязан оставаться свободным.

Стек при этом поднимается на внутренних портах и ничего не занимает:

```bash
# .env на сервере
API_HOST_PORT=3001      # публикуется только на 127.0.0.1
PORTAL_HOST_PORT=8080   # публикуется только на 127.0.0.1
```

`127.0.0.1:` в публикации портов — обязательная часть. Без него Docker откроет порт
наружу, и вы получите лишнюю точку входа в обход прокси.

### Как отдать домен

Дальше нужен способ доставить трафик до `127.0.0.1:8080`. Варианты по убыванию
безопасности для соседей:

1. **Cloudflare Tunnel** — отдельный контейнер `cloudflared`, трафик идёт из Cloudflare
   в туннель. Не занимает портов вообще, не трогает certbot, TLS на стороне Cloudflare.
   Самый безопасный вариант, если домен уже за Cloudflare.
2. **Добавить хост в существующий обратный прокси** — если 443 держит Xray или nginx с
   маршрутизацией по SNI, домен добавляется там. Требует правки чужого конфига.
3. **Свой прокси на свободном порту** — работает, но требует правила в Cloudflare
   (Origin Rule), потому что по умолчанию Cloudflare ходит на источник по 443.

### Сборка образов под чужую архитектуру

Если локальная машина и сервер различаются по архитектуре (например, Mac на arm64 и
сервер на x86_64), образы собираются с явным указанием платформы:

```bash
docker build --platform linux/amd64 -f apps/api/Dockerfile -t luciferus-api:amd64 .
docker build --platform linux/amd64 -f apps/portal/Dockerfile -t luciferus-portal:amd64 .

docker save luciferus-api:amd64 luciferus-portal:amd64 | gzip -1 \
  | ssh root@сервер 'gunzip | docker load'
```

Собирать на самом сервере не стоит: сборка Next.js временно занимает больше гигабайта,
а на машине с другими сервисами это риск. Готовые образы занимают около 500 МБ.

На сервере тег образа задаётся переменной, чтобы конфиг не расходился с репозиторием:

```
IMAGE_TAG=amd64
```

## Обновление

```bash
docker compose -f docker-compose.prod.yml pull    # если образы из реестра
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml run --rm migrate
```

Миграции применяются отдельной командой, а не при старте: так рестарт контейнера не
превращается в неявную миграцию схемы.

## Что проверить после развёртывания

```bash
curl -s http://127.0.0.1:3001/v1/health          # {"ok":true,"db":"up","redis":"up"}
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/sdk/v1.js
```

Если что-то не сходится — смотрите логи: `docker compose -f docker-compose.prod.yml logs -f api`.
